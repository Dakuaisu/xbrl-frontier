### notes
BOTTOM LINE FOR THE PROJECT: (a) MLX/mlx-lm can LoRA/QLoRA every target model (Qwen3, Qwen2.5, Llama 3.2, Gemma 3, SmolLM3, Phi-4-mini) and reports tokens/sec + peak memory out of the box, but there is NO published small-model throughput; the user must benchmark (a 10-minute run gives the number). (b) The load-bearing MLX limitation for ~1k-token (and especially table-heavy multi-k-token 10-K) examples is attention-backward memory: until PR #4563 ships in a release, training materializes an L x L attention matrix (PR cites 24.63 GiB -> 1 GiB savings at the longest shape), consistent with the 121 GB peak seen for an 8B LoRA at seq 8192 on an M3 Max. Keep max_seq_length <= 2048-4096 on 32-64 GB Macs, batch 1-2, --grad-checkpoint, QLoRA base. (c) Full fine-tuning is supported (--fine-tune-type full) but undocumented memory-wise; one 8B bf16 run at seq 5000 hit Metal OOM on a 128 GB Mac Studio. (d) Export: mlx-lm writes its own adapter format (lora_a (in,r) / lora_b (r,out), 'scale' not alpha, last-16-layers default, no 'base_model.model.' prefix). There is no PEFT import/export in mlx-lm (PR #1120 closed unmerged Aug 2026), so a ~50-line converter is needed: transpose, rename, prefix, lora_alpha = scale*r (default 160 for r=8, scale=20), target_modules, layers_to_transform. vLLM then serves it with --enable-lora (max-lora-rank default 16; Qwen3/Gemma3/Llama/Phi3/SmolLM3 all LoRA-capable). (e) MLX 4-bit (affine) checkpoints are NOT loadable by vLLM (no MLX in its quantization list) nor convertible by llama.cpp (converter lacks MLX .scales/.biases; two issues closed not-planned/stale; mlx-lm's own gguf.py raises NotImplementedError for quantized models and only handles llama/mistral/mixtral). The workable path is mlx_lm.fuse --dequantize -> fp16 HF safetensors -> convert_hf_to_gguf.py (GGUF) or AWQ/GPTQ/llm-compressor re-quantization for vLLM; note dequantized-4-bit base != original bf16 base. (f) GPU alternative: Unsloth Core is Linux/Windows-only (Apple 'in the works'), though Unsloth Studio GUI can train on macOS via MLX. Budget sketch (derived, UNVERIFIED arithmetic): 50k-200k examples x ~1k tokens = 50M-200M tokens/epoch. LitGPT measured llama-3.2-3b LoRA at ~8 examples/s on 1x A10G at seq 512 on short Alpaca examples; scaling to 1k-token examples (~1.6 ex/s assumed) gives roughly 9 h (~$9 at $1.006/h g5.xlarge) for 50k and ~35 h (~$35) for 200k per epoch, halved with Unsloth's 1.5-2x claim, and ~3-4x faster on an A100 ($1.99/h Lambda, $1.19-1.59/h RunPod 80GB). L4 is cheapest (~$0.44-0.81/h) but slower than A10G. Managed Together.ai LoRA at $0.34-0.38/M tokens is ~$17-19 (50M) to ~$68-76 (200M) per epoch with zero ops. On a Mac at an assumed 500-1,500 tok/s for a 3B QLoRA, the same epoch is ~9-110 h, i.e., Mac is fine for the 1-5k-example pilot and ablations, but a rented A10G/A100 (or Together) is the realistic path for 50k-200k examples. (g) Publication relevance: the arXiv API shows no paper benchmarking MLX fine-tuning throughput, and only one (2606.31048) that even uses MLX LoRA, so reporting measured Mac vs GPU training cost/latency is itself a minor novelty, though it is orthogonal to the FinTagging serving-cost claim.
