# D4: final adapter on the pinned FinNI set

This is a private owner-run workflow. Do not publish the notebook output, dataset snapshot, token or prediction files. The CPU
probe confirmation reported by the owner is not a GPU measurement. The only tracked deliverable here is tooling; actual outputs
belong under ignored `data/kaggle/` and `data/scores/`.

## Before each GPU session

1. From the repository root, rebuild the importable notebook and check the budget:

   ```sh
   PYTHONPATH=. .venv/bin/python -m scripts.d4_build_notebook
   PYTHONPATH=. .venv/bin/python -m scripts.d4_budget --planned-hours 8
   .venv/bin/kaggle kernels list --user adnanrashid29 --sort-by dateRun --page-size 100 --csv
   ```

   The builder checks the final adapter, the current T-039 audit and the D3 generator. The budget command uses the live quota,
   current configured caps, ledger and statuses of recorded project kernels, reserving the requested session length. It stops on
   unknown statuses or cap failure. Independently inspect the account's UI/kernel list for any unrecorded active GPU session;
   do not start if any reservation, submission outcome or quota is uncertain. Repeat these checks before session 2, including after
   the weekly refresh. A weekly refresh does not reset the cumulative project cap. After a refresh, the command refuses until the
   closed week's actual usage and the next refresh are reconciled as a new `quota_reset` record in `data/kaggle/runs.jsonl`; follow
   the existing ledger convention and retain the prior weeks rather than replacing them. Do not fabricate a week total from a
   reading taken after reset or double-count overlapping sessions.

2. **Hard-timeout gate:** the notebook's deadline is not a provider-enforced kill. The previously observed Kaggle UI save dialog
   did not expose a kernel timeout. Before either GPU submission, verify that the actual submission mechanism can enforce the
   requested hard limit of at most eight hours. If the UI does not expose that setting, **do not submit through the UI** until the
   owner has a verified way to set it. The CLI documents `kernels push --timeout` in seconds, but secret attachment and behavior for
   this particular UI draft through CLI have not been verified; do not assume it is an equivalent or retry an ambiguous push.

## Session 1: private draft and secret check

1. In Kaggle, create a **new private notebook** with a unique slug, for example `xbrl-frontier-d4-s1`; first confirm that slug has
   no prior version. Import `notebooks/d4_gpu.ipynb`. Under **Add Input**, attach the private `xbrl-frontier-src` and
   `xbrl-frontier-corpus` datasets and the completed `xbrl-frontier-run-1p7b-s1-sess4` notebook output (version 3).
   The internal corpus is not the FinNI evaluation input. The imported notebook embeds the new D4 helpers and current configuration; the mounted source supplies the old generator
   and its dependencies, all checked against local D3 source hashes. Do not attach or upload a copy of the gated FinNI data.
2. Set Accelerator to **None / CPU**, enable Internet, and attach the authorized `HF_TOKEN` through **Add-ons → Secrets** to this
   notebook. Do not paste the token in a cell, chat, command line or logs. Leave `MODE = 'CPU_PROBE'`; run the cell. It requires
   CPU, obtains the secret in memory, downloads the pinned snapshot only to temporary `/tmp`, checks its shard hash and row count,
   and emits only `D4_ACCESS_OK` with revision, count and hash, or a sanitized failure. Do not continue on failure. A successful
   probe in a different notebook or CI is not proof that this draft's secret attachment works.
3. Stop the CPU draft session. Re-run the budget and account-activity checks above. Set Accelerator to **GPU T4**, keep Internet and
   the secret enabled, and change `MODE` to `GPU`. Set `KERNEL_REF` to the exact expected `owner/slug/version` of the next saved
   run, such as `adnanrashid29/xbrl-frontier-d4-s1/1` only if version history confirms that is the next version. Leave both
   `PREVIOUS_*` values empty. If another version can be created concurrently, stop instead of guessing.
4. Immediately before submitting, obtain a UTC timestamp with `date -u '+%Y-%m-%dT%H:%M:%SZ'`, put it in `SESSION_START_UTC`, and
   choose **Save Version → Save & Run All** once, only after the hard-timeout gate is satisfied. This pre-submission timestamp makes the application's deadline
   include queue and notebook startup time; its configured stop margin is applied before the deadline. It does not itself enforce a
   provider timeout or interrupt a stuck setup operation. If submission is ambiguous, inspect version history; never submit again
   merely because a response is missing. Check the actual saved version and status read-only. A mismatch with `KERNEL_REF` blocks
   collection and resume; do not relabel it.

## Collect session 1 and decide whether session 2 is needed

Replace the example reference only with the exact version observed in Kaggle version history:

```sh
PYTHONPATH=. .venv/bin/python -m scripts.d4_collect \
  --kernel adnanrashid29/xbrl-frontier-d4-s1/1 \
  --out data/kaggle/d4-session1
```

The collector polls that version every minute, downloads into a temporary directory, discards the provider log, and copies only
validated output files into a new private local directory. It checks the preflight, receipt, metadata hash and exact unique IDs.
It prints a sanitized `receipt_sha256`, missing count and cutoff count. Keep the digest and exact kernel reference for session 2.
If the receipt or metadata is absent or inconsistent, stop; do not manufacture a receipt. If coverage is complete, it runs the
oracle suite and the scorer locally and refuses to overwrite an existing score. If partial, it does **not** score.

## Session 2: only if session 1 is partial

After the quota refresh when needed, repeat **Before each GPU session**. Create a new private notebook/slug, import the same rebuilt
`notebooks/d4_gpu.ipynb`, attach the same datasets and session-4 output, and add the **verified session-1 notebook output**. Run the same CPU secret check in
the new draft before allocating a GPU. Then stop CPU, select the T4, and set:

- `MODE = 'GPU'` and `KERNEL_REF` to session 2's expected exact `owner/slug/version`.
- `PREVIOUS_KERNEL_REF` to the exact session-1 version collected above.
- `PREVIOUS_RECEIPT_SHA256` to the digest printed by the successful session-1 collector, not a hash copied from an unverified run.
- `SESSION_START_UTC` to a fresh UTC timestamp obtained immediately before this submission.

The notebook finds exactly one attached receipt with that digest, verifies its version and previous metadata/prediction hashes and
generation identity, rejects duplicates/extras and refuses a prior complete set. The D3 continuous generator then copies those rows
and submits only IDs missing from the pinned full set; length-cutoff outputs remain written and are not retried. Reconfirm the hard
provider timeout and budget, then submit once. Collect the actual version using the same command with session 2's exact reference
and a new destination, for example:

```sh
PYTHONPATH=. .venv/bin/python -m scripts.d4_collect \
  --kernel adnanrashid29/xbrl-frontier-d4-s2/1 \
  --out data/kaggle/d4-session2
```

Only if exact full coverage and oracle calibration pass does the collector write `data/scores/d4-final-finni.json`. A partial or
failed run is not a full-set score. Report the observed provider status and actual GPU quota use separately; never infer completion
from a submission receipt.
